## Testing

When the story has testable logic, work test-first in vertical slices: write one
failing test for a behavior, add the minimal code to pass it, repeat — do NOT write
all tests first and then all the code.

- **Test at the seams the story/PRD names** (the public boundary where behavior is
  observed without reaching inside). If none is named, use the HIGHEST existing seam;
  prefer existing seams over new ones and the fewest possible.
- **Test observable behavior through the public interface, not implementation.** Two
  anti-patterns to avoid: (a) implementation-coupled tests — asserting private state,
  mocking internal collaborators, or querying a DB instead of using the interface;
  they break on refactor though behavior is unchanged. (b) tautological tests — where
  the expected value is recomputed the same way the code does it, so it can never
  disagree; expected values must come from an independent source (a known-good
  literal, a worked example, or the spec).

## Language of the code

Write the code in English, whatever language the story, the PRD, the glossary
or the progress file is in: identifiers, file and type names, test names,
comments and doc comments, log and error messages, database tables, columns and
migration names, JSON keys, and the body of your commit message.

- **Text the product shows or sends stays in the language the story asks for** —
  UI labels, notifications, messages to users, prompts sent to a model. That is
  product content, not code.
- **A domain term from a non-English glossary (e.g. `CONTEXT.md`) gets one fixed
  English name in code.** Use the one the code already has. For a new term, pick
  one and add the mapping to Codebase Patterns (e.g. "Aufnahme → `Recording`") so
  every later story uses the same word. The glossary's "Avoid" lists govern how
  we talk about the product, not what the code calls it.
- **This holds even where earlier code in the repo is in another language.** Do
  not copy that; do not rename it either, beyond what your story touches.

## Consolidate Patterns

If you discover a **reusable pattern** that future iterations should know, add it to the `## Codebase Patterns` section at the TOP of `{{PROGRESS_PATH}}` (create it if it doesn't exist). This section should consolidate the most important learnings:


Only add patterns that are **general and reusable**, not story-specific details.

Every iteration reads this section before it starts, so keep it short:

- **One line per pattern**, a sentence or two. The story entry is the place for
  the details and the reasoning.
- **Sharpen an existing pattern rather than adding one** that overlaps it, and
  remove a pattern that has stopped being true.
- Keep the whole section under about 24 KB.

## When Only a Person Can Unblock the Story

Nobody is watching this run. Some things stop a story that no amount of work on
the code can get past, and trying again only burns the night. For those — and
ONLY those — report the story blocked instead of done:

- a system dialog that nobody will answer (a keychain prompt from `codesign`, a
  "wants to access" prompt) or a command that hangs waiting on one
- a locked password manager or signing agent (1Password, gpg, an SSH key that
  needs unlocking to sign commits)
- a missing OS permission (macOS privacy/TCC, accessibility, full disk access)
- a missing account, credential, access right, or piece of hardware
- a decision, or a contradiction in the PRD, that only the person who wrote it
  can settle (two criteria that exclude each other, a team ID that does not match
  the project)

Failing tests, build errors, lint errors, a missing dependency you can install,
and bugs in your own code are **never** blocked — fix them. When in doubt, it is
not blocked.

If you are blocked:
1. Commit the finished, working part of the story as usual, with the same
   message as above (`feat: {{PRD_NAME}}/{{STORY_ID}} - {{STORY_TITLE}}`). Skip
   this if nothing is finished or it does not pass the quality checks.
2. Append a progress entry saying what is done, what is left, and exactly where
   it stopped.
3. Output `<chief-blocked>what blocks the story · what the person has to do</chief-blocked>`
   — one or two sentences, concrete enough to act on without reading the log,
   e.g. `<chief-blocked>codesign waits on a keychain prompt for the "Developer ID"
   certificate · allow codesign to use the key in Keychain Access, then set the
   story back to todo</chief-blocked>`.
4. Stop. Do NOT output <chief-done/>, and do not try again: the story is set
   aside until the person has acted, and the run moves on to other stories.

## Stop Condition

After implementing the story:
1. Review EACH acceptance criterion one by one and verify it is met
2. Only if ALL criteria pass: output <chief-done/>
3. If a criterion cannot be met because of something only a person can resolve
   (see above): output <chief-blocked>…</chief-blocked> instead
4. If any other criterion is NOT met: end your response WITHOUT <chief-done/>
