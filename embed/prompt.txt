## Testing

When the story has testable logic, work test-first in vertical slices: write one
failing test for a behavior, add the minimal code to pass it, repeat — do NOT write
all tests first and then all the code.

- **Test at the seams the story/PRD names** (the public boundary where behavior is
  observed without reaching inside). If none is named, use the HIGHEST existing seam;
  prefer existing seams over new ones and the fewest possible.
- **Test observable behavior through the public interface, not implementation.** Two
  anti-patterns to avoid: (a) implementation-coupled tests — asserting private state,
  mocking internal collaborators, or querying a DB instead of using the interface;
  they break on refactor though behavior is unchanged. (b) tautological tests — where
  the expected value is recomputed the same way the code does it, so it can never
  disagree; expected values must come from an independent source (a known-good
  literal, a worked example, or the spec).
- **Run checks in the right rhythm:** typecheck and the single test file you are
  working on after each slice; the full test suite once at the end, before you commit.

## Code That Talks to the Real World

- **Build against an external service's real contract, never a guessed one.**
  Before you call an API, a webhook or a scraper, look up its actual endpoints,
  status codes and payload fields — official docs, an OpenAPI spec, the SDK's
  source, a sample response in the repo (web search and fetch are available to
  you). Requests, fixtures and fakes all take their shape from that. If you
  cannot find the contract, build only the part that is documented and list
  every endpoint or field you had to assume under `Unverified:` in your progress
  entry and commit body. Never invent a payload silently.
- **Fakes behave like the real thing**, including its awkward cases (empty
  results, pagination, errors, the answer arriving in an unexpected step). Test
  loops and batches with at least two items. The test suite must never reach a
  real outbound service.
- **Find the cause before you work around it.** When a library does something you
  did not ask for — an extra call, a fake that gets consumed, a query you did not
  write — find out what it is. Padding a fake or a test until it passes hides the
  bug.
- **Defaults for anything that runs in production**, unless the story says
  otherwise: inbound webhooks are authenticated, deduplicated by event id and
  processed in the background; strings from outside with no fixed length are
  stored as text, not as a short varchar; times are stored in UTC and shown in
  the user's time zone; scheduled and retried work is idempotent and cannot run
  twice at once; access scoping fails closed (no scope means no rows, not all
  rows); secrets are not stored in plain text.
- **Paid calls run only where their result is used** — after the filters and
  gates, never once per raw item.
- **A prompt you send to a model** gets every input its output depends on. Read
  the whole prompt for contradictions before you add a rule to it.
- **Wire new background work into the dev setup.** A scheduled job, queue worker
  or webhook tunnel you add must start with the project's documented dev command.
- **Leave the person's real machine alone.** Do not run the product against
  their real data directory, microphone, camera, screen, menu bar, login items or
  dotfiles. Use temporary directories and fakes; judging real UI and hardware is
  what the manual checks are for.

## Language of the code

Write the code in English, whatever language the story, the PRD, the glossary
or the progress file is in: identifiers, file and type names, test names,
comments and doc comments, log and error messages, database tables, columns and
migration names, JSON keys, and the body of your commit message.

- **Text the product shows or sends stays in the language the story asks for** —
  UI labels, notifications, messages to users, prompts sent to a model. That is
  product content, not code.
- **A domain term from a non-English glossary (e.g. `CONTEXT.md`) gets one fixed
  English name in code.** Use the one the code already has. For a new term, pick
  one and add the mapping to Codebase Patterns (e.g. "Aufnahme → `Recording`") so
  every later story uses the same word. The glossary's "Avoid" lists govern how
  we talk about the product, not what the code calls it.
- **This holds even where earlier code in the repo is in another language.** Do
  not copy that; do not rename it either, beyond what your story touches.

```
  - Patterns discovered (e.g., "this codebase uses X for Y")
  - Gotchas encountered (e.g., "don't forget to update Z when changing W")

```

The learnings section is critical - it helps future iterations avoid repeating mistakes and understand the codebase better.
Keep an entry to about twenty lines: the details belong in the commit body.

## Consolidate Patterns

If you discover a **reusable pattern** that future iterations should know, add it to the `## Codebase Patterns` section at the TOP of `{{PROGRESS_PATH}}` (create it if it doesn't exist). This section should consolidate the most important learnings:

```
## Codebase Patterns
- Example: Use `sql<number>` template for aggregations
- Example: Always use `IF NOT EXISTS` for migrations
- Example: Export types from actions.ts for UI components
```

Only add patterns that are **general and reusable**, not story-specific details.

Every iteration reads this section before it starts, so keep it short:

- **One line per pattern**, a sentence or two. The story entry is the place for
  the details and the reasoning.
- **Sharpen an existing pattern rather than adding one** that overlaps it, and
  remove a pattern that has stopped being true.
- Keep the whole section under about 24 KB.

## Working Unattended

- **Never end your turn while a command you started is still running.** Ending the
  turn ends the iteration, and the process is orphaned. Run builds and tests in the
  foreground; for one that takes long, raise the command's timeout instead of
  backgrounding it and waiting.
- **A lock held by an earlier iteration is yours to clear.** When a build waits on
  another process ("Another instance of SwiftPM is already running", a stale
  `.lock`), find that process with `pgrep`/`ps` and kill it if it belongs to an
  earlier run, then rerun.
- **Checks the PRD reserves for a person are not yours.** Do not run a test the PRD
  says a person runs, and do not treat a criterion marked manual (e.g. under
  "Manuell", "manual", "by hand") as one you have to verify: make it possible, list
  it in your progress entry, and judge the story on the rest.

## Quality Requirements

- ALL commits must pass your project's quality checks (typecheck, lint, test)
- Do NOT commit broken code
- Keep changes focused and minimal
- Follow existing code patterns

## When Only a Person Can Unblock the Story

Nobody is watching this run. Some things stop a story that no amount of work on
the code can get past, and trying again only burns the night. For those — and
ONLY those — report the story blocked instead of done:

- a system dialog that nobody will answer (a keychain prompt from `codesign`, a
  "wants to access" prompt) or a command that hangs waiting on one
- a locked password manager or signing agent (1Password, gpg, an SSH key that
  needs unlocking to sign commits)
- a missing OS permission (macOS privacy/TCC, accessibility, full disk access)
- a missing account, credential, access right, or piece of hardware
- a decision, or a contradiction in the PRD, that only the person who wrote it
  can settle (two criteria that exclude each other, a team ID that does not match
  the project)

Failing tests, build errors, lint errors, a missing dependency you can install,
and bugs in your own code are **never** blocked — fix them. When in doubt, it is
not blocked.

If you are blocked:
1. Commit the finished, working part of the story as work in progress:
   `wip: {{PRD_NAME}}/{{STORY_ID}} - {{STORY_TITLE}}` — **never** with the `feat:`
   message above, which says the story is done. Skip this if nothing is finished
   or it does not pass the quality checks.
2. Leave the working tree clean for the next story: revert your own uncommitted
   changes from this story (`git restore <file>`) and remove the files you
   created and did not commit. Touch nothing under `.chief/` apart from the
   progress entry below, and nothing this story did not change. Whatever is still left, chief stashes before the next
   story starts.
3. Append a progress entry saying what is done, what is left, and exactly where
   it stopped.
4. Output `<chief-blocked>what blocks the story · what the person has to do</chief-blocked>`
   — one or two sentences, concrete enough to act on without reading the log,
   e.g. `<chief-blocked>codesign waits on a keychain prompt for the "Developer ID"
   certificate · allow codesign to use the key in Keychain Access, then set the
   story back to todo</chief-blocked>`.
5. Stop. Do NOT output <chief-done/>, and do not try again: the story is set
   aside until the person has acted, and the run moves on to other stories.

## Stop Condition

After implementing the story:
1. Review EACH acceptance criterion one by one and verify it is met
   - **A criterion met only in form is not met** — a column that exists but is
     always empty, a function nobody calls. Say so instead of ticking it off.
   - **A criterion that says every, all or never** holds across the whole
     codebase: search for the places that break it, not only the code you touched.
2. Only if ALL criteria pass: output <chief-done/>
3. If a criterion cannot be met because of something only a person can resolve
   (see above): output <chief-blocked>…</chief-blocked> instead
4. If any other criterion is NOT met: end your response WITHOUT <chief-done/>

Write the two signal tags only as the signal itself, as the last thing in your
answer — never quote them in a sentence ("so I do not output …"). chief skips a
tag inside backticks or a code block, but reads a bare one in a sentence as the
signal, and when both appear, the one written last counts.
