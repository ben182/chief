1. Study the commits above. Use `git show <hash>`, `git log`, and read the

3. Do NOT commit anything and do NOT run git add — the file is committed for you

   output <chief-done/> and stop.

## What the summary must contain

Write it for a developer (likely future-you) who was away while this ran and now
needs to pick it up. Use these sections, in this order:

# Run Summary

A 2–4 sentence overview: what was this run about, what got done.

## Was wurde gebaut
Concrete list of the features/changes that landed, grouped sensibly. Reference
the relevant files/modules so the reader knows where each piece lives.

## Wie kann ich es testen
The most important section. Give concrete, copy-pasteable steps to try the new
functionality: commands to run, what to click/call, what the expected result is.
Mention any automated tests that were added and how to run them.

## Wo finde ich das Neue
Point to where the new functionality lives — files, screens, endpoints, CLI
commands, config keys — so the reader can navigate straight to it.

## Offene Punkte
Anything left undone: parked/needs-review stories, known gaps, TODOs, or
follow-ups you noticed while reading the diff. If there is nothing, say so.

Write in German (matching the section headings), be specific, and prefer real
file paths and commands over vague description. Keep it tight — no filler.
