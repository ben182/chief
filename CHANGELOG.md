# Changelog

All notable changes to Chief are documented in this file.

## [Unreleased]

### Features
- **Settings edits reach the run you are watching** — the review, consolidation, watchdog and keep-awake settings were read once, when a run started, and copied into the loop. That is the wrong moment for every one of them: you find out the review isn't earning its cost by watching it fix nothing for three stories, and by then the only way to act on it was to stop the run. A loop started by the manager now re-reads them from the manager each time it needs one, so switching the review off, moving it to a cheaper model, or raising the watchdog timeout applies to the rest of the run — the next review, the next agent invocation, the end-of-run consolidation pass. An in-flight review keeps the settings it started with rather than being restarted, and `loop.keepAwake` is reconciled on a 5s ticker so it can be switched **on** mid-run too, which is the direction people actually reach for. A `Loop` driven without a manager keeps using the values it was configured with, so nothing about using the package directly changes. `onComplete.*` already worked this way. `agent.provider` / `cliPath` / `model` still need a restart — the CLI is resolved once at startup — and that is now written down rather than left to be discovered
- **Config edits publish a new config instead of editing the one in use** — with a running loop reading these settings from its own goroutine, writing through the shared `*config.Config` would have been a data race on every field the overlay can reach, on every keystroke. The TUI now folds the overlay's values into a fresh copy and hands that to the manager under its lock, so a reader sees either the old config or the new one and never a half-applied edit. The copy is a true snapshot: every field is a value type except the two `enabled` switches, which are copied rather than shared at both ends. The `Manager`'s sleep guard became a two-method interface at the same time, so the reference counting can be tested without spawning `caffeinate`
- **Settings covers the whole config file again** — the overlay carried a hand-picked seven of the config's settings, so every key added since had been reachable only by opening `.chief/config.yaml` in an editor: the per-phase `review.model` / `consolidate.model` shipped one release earlier were invisible in the UI that exists to expose exactly that, and so were `agent.provider`, `agent.cliPath`, `agent.model`, `loop.watchdogTimeoutSeconds` and both passes' `enabled` / `skill` / `instructions`. All seventeen keys now have a row, in three new sections (**Agent**, **Review**, **Consolidate**). Two new field types come with them. `enabled` is a `*bool` where nil is a *third, meaningful state* — the review and consolidation passes derive their on/off from whether a skill or instructions are configured — so rendering it as a plain Yes/No would have erased that the first time anything in the overlay was saved; `Enter` instead cycles **Default → Yes → No → Default**, the value column shows what *Default* currently resolves to (`Default (on)` / `Default (off)`, following the sibling skill and instructions fields as they're edited), and an untouched switch writes no `enabled:` key at all. The agent provider is a closed set that `agent.Resolve` validates, so it cycles through the five supported CLIs rather than accepting free text that would only surface as a failed run — a name it doesn't recognise (hand-edited YAML, or one dropped in a later version) cycles back to the top instead of trapping. `loop.watchdogTimeoutSeconds` takes digits only, and clearing it falls back to the built-in 300s. Unset values that mean something other than "off" now say so — `sonnet (default)`, `claude (default)`, `300 (default)`, `(found in PATH)` — instead of a uniform `(not set)`. The list is more than twice as tall as it was, so the modal grows to fit it on a tall terminal and scrolls on a short one, with `⋯` marking that it continues above or below, and a value too wide for its column is now shortened rather than wrapped — lipgloss wraps an over-long line instead of letting it overhang, which cost the box rows it had already sized itself for and pushed settings off the bottom, easy to hit with free-form review instructions. Two tests pin the overlay to `config.Config` by reflection, one for coverage and one for the round trip, so a key added to the config from here on fails the build until it has a row that also applies

- **Review and consolidation run on their own model — Sonnet by default** — both agents only ever read code that is already written and committed, yet running them on the build model made them a large share of a run's bill: on a measured 7-story Opus run the reviews alone were about a third of the cost, since each pass re-reads a story's diff on the most expensive model available for work that never writes a line of new design. Both phases now default to **Sonnet** instead of inheriting the build agent's model, and each is overridable on its own via `review.model` / `consolidate.model` (e.g. `haiku` to go cheaper still, `opus` when you want the big one after all). On that same run the two phases come out at roughly $30 against $143. The model is applied **per invocation** through a new optional `loop.ModelSwitcher`: the Claude provider hands back a copy of itself running on the phase's model, so the build agent's provider is never mutated and an empty `agent.model` still passes no `--model` at all. Providers whose CLI takes no model simply don't implement the interface, which makes the two new keys inert there rather than an error. One thing to know if you've pinned a build model of your own (e.g. a local model via LM Studio): `agent.model` is deliberately untouched by this, so set `review.model`/`consolidate.model` to the same value to point those phases at it too
- **Chief warns before a run when the Mac can fall asleep** — a run is a walk-away workflow, so the machine suspending mid-story is discovered hours later, and none of the lost wall-clock time is recoverable. Two hazards are visible up front rather than in hindsight: on battery a closed lid suspends a MacBook no matter what sleep assertion Chief holds (clamshell sleep isn't software-preventable on Apple Silicon), and `loop.keepAwake` may simply be switched off. So a run that looks at risk now opens a **"Mac May Fall Asleep Mid-Run"** dialog before the first story starts, naming the reason it fired and the fix for it (plug in / leave the lid open, or re-enable the setting), with *Start anyway* / *Cancel* — and **Cancel preselected**, so a reflexive Enter doesn't launch the run. When both hazards apply, one dialog explains both. It is the last gate before a run begins, and confirming it goes straight through so nothing is asked twice. It deliberately re-asks on **every** start: the machine can be unplugged between two runs, and a warning you can dismiss for good stops telling you anything. Everything about the probe is best-effort — `awake.CurrentPowerSource` reports an unknown power source when `pmset` is missing, fails, or the platform has no such query, and an unknown power source raises no dialog at all. A disabled `loop.keepAwake` still does; that one you set yourself
- **The completion screen accounts for time the Mac spent asleep** — every duration Chief shows is measured against the monotonic clock, which stops while the machine is suspended. That makes those figures pure *working* time, which is the right number — but it also left a run looking far shorter than the clock on the wall said it took, with nothing on screen to explain the gap (on one measured run, 2h53m displayed against 3h47m elapsed). When sleep is detected, the completion screen now adds a line under "Completed in" — `Mac slept 56m00s during the run`. A new `awake.SleepTracker` compares the wall clock against the monotonic clock on the existing per-second elapsed tick and records any divergence beyond a minute as sleep, so ordinary scheduling jitter isn't mistaken for a nap. The answer is anchored on the run's start, which keeps a second run in the same session from inheriting the first one's naps and keeps sleep that happened *before* the run — discovered by the first sample after it started — off its bill. Nothing else changes: no live warning during the run, no persistence (a restarted Chief counts from zero), and story times, the total and the ETA all stay working time
- **Branch/origin divergence is caught before a run starts, not after it** — a branch that is behind `origin` accepts every commit a run makes and only fails at the very last step, when the push is rejected as non-fast-forward. The failure mode is entirely about timing: the same question is answerable in one fetch up front, but Chief asked it four hours and a few hundred dollars of agent time too late, leaving the user to reconcile the branch by hand from a completion screen full of git hints. Starting a PRD now compares the branch the loop will commit to against `origin/<branch>` first, and a diverged branch raises a **"Branch Behind Remote"** dialog before any story runs. The dialog reports both counts (what origin has that you don't, and vice versa) and offers to reconcile — naming which operation it will be, since the two differ in risk: a branch with no local commits of its own is **fast-forwarded** (cannot conflict), while one carrying local commits is **rebased** onto the remote tip so those commits end up on top. A rebase that conflicts is aborted, restoring the branch exactly as it was, and the start is stopped rather than walking back into the rejected push. "Start anyway" is there for when you know better. Notably it does *not* offer a force-push: on a branch that is behind, the remote commits are ones you don't have, so forcing would silently discard them. Every way of not being able to answer — no `origin`, no network (the fetch is capped at 15s), a branch the remote has never seen — lets the run start normally, because a preflight that blocks an offline user is worse than the problem it prevents. Worktree runs are skipped (their branch is created fresh in a directory of its own) as are `main`/`master`, which are never auto-pushed
- **The machine stays awake while a loop runs** — a run is a walk-away workflow, which is exactly why it kept getting cut short: nobody touches the keyboard for an hour, macOS counts that as idle, and the Mac sleeps mid-story with the agent frozen until someone came back and wiggled the mouse — turning a 40-minute run into a run that finished whenever you next sat down. While a loop is running, Chief now holds a sleep assertion (`caffeinate -i -s` on macOS) for the machine but not the display, so the screen still goes dark and only the sleep is held off. The assertion is reference counted, so parallel PRDs share one and the machine is released as soon as the last loop ends — including when the run errors, is stopped, or is paused, since the release is deferred alongside the loop. The helper is also tied to Chief's own PID, so a `kill -9`'d Chief can't leave the machine pinned awake for good. On by default (`loop.keepAwake`); toggle it in Settings (`,` → Loop → Keep machine awake) or set `loop.keepAwake: false`. Best-effort throughout — a missing `caffeinate` is swallowed rather than failing a run — and currently macOS only, a no-op elsewhere. One thing no assertion can override: a MacBook with a closed lid and no external display still sleeps
- **End-of-run consolidation pass — one agent that finally sees the whole run** — the review agent judges one story at a time, which is the right scope for "is this story correct?" and structurally the wrong scope for "is the result coherent?". Because every story is built by a separate agent with a fresh context, story 3 cannot know that story 7 will need the same date helper, and story 7 cannot see the one story 3 already wrote: both agents do something reasonable, both commits pass their own review, and the run ends with two helpers for one job. No per-story reviewer can catch this — at the moment it reviews story 3, the duplicate does not exist yet. Repeat across forty stories and a run leaves forty locally-clean commits on top of an incoherent whole. The new `consolidate` config adds a second, differently-scoped quality agent that runs **once**, after the last story, and is the only agent that ever sees the entire run. It looks for exactly the fresh-context failure modes — parallel implementations of the same thing, competing patterns for one concern, near-duplicate code that wants one abstraction, leftovers from abandoned approaches, drift from the codebase's own conventions — and explicitly leaves alone anything the tooling enforces, bugs and unmet criteria (the reviewer's job; it writes them down instead), and speculative restructuring. Three properties keep it safe: it is **scoped to this run** (`StartRef..HEAD`, the same window the run summary uses, handed to the loop by the Manager so both agree exactly — so a followup run never reopens work an earlier run already reviewed, summarized or pushed, and a run that landed no commits or has no determinable window is skipped rather than let loose on the whole branch); it is a **pure refactor in its own commit** (behavior must not change, tests may not be bent to pass, and the work lands as one separate `refactor: consolidate <name> run` commit — never amended into a story commit — so it can be reviewed and reverted alone, with the prompt instructing the agent to run the project's checks and **revert rather than commit** if it can't get them green); and it **never blocks the run** (best-effort like the review — a crash or an unfinished pass is surfaced as an event but the stories stay done, bounded at 2 attempts since each pass reads the whole run's diff). It runs *before* `EventComplete`, so the run summary describes the consolidated result and the push/PR carries it, and it also runs when a run ends on the iteration cap, since such a run is equally over and equally seam-ridden. Enable with `consolidate.enabled: true`, or by setting `consolidate.skill` / `consolidate.instructions` (both optional and additive, mirroring `review`). Off by default, deliberately: it edits code that already worked and was already signed off. The pass shows up in the log as `🧹 Consolidating this run's commits` → `✓ Consolidation complete`. Arguably its most valuable output isn't the refactor but the `progress.md` note: being the only agent that sees the whole run, it records the pattern the run *should* have followed from the start — which is what the next run's fresh-context agents read before they start diverging again
- **PRD-namespaced story commits — story IDs are no longer ambiguous across PRDs** — story IDs are only unique *within* a PRD and their numbering restarts per PRD, so two PRDs both using the generic `US-` prefix each own a `US-001`. Chief now prefixes every story commit with the PRD's name: the build agent commits as `feat: <prd-name>/<ID> - <title>` (where `<prd-name>` is the PRD's directory under `.chief/prds/`, which is also its `chief/<name>` branch suffix). Because `<prd-name>+<ID>` is a genuinely unique key, commit lookup (`storyHasCommit`'s completion check, the per-story diff viewer, and the run-summary's `feat:`-subject match) now keys on that prefix instead of on an exact story-title match. This removes the previous fragility where editing a story's title in `prd.md` after it was committed made Chief lose the commit — and it correctly disambiguates two PRDs that reuse the same ID *and* the same title, which the old title-only matching could not. Commits authored before this change (`feat: <ID> - <title>`, no namespace) still resolve via a legacy fallback, so in-flight PRDs keep working. Authoring guidance (`chief new`/`followup` prompts, PRD schema docs) now also recommends a feature-scoped ID prefix (`AUTH-`, `BILL-`) over the generic `US-` so IDs read unambiguously across PRDs, though this is only a readability convention — correctness no longer depends on it
- **Bare `chief` opens the PRD for your current branch** — the branch inference that `chief edit`/`chief followup` already do now also drives the default TUI. Running `chief` with no name from within a PRD's own `chief/<name>` branch opens *that* PRD (printing `Using PRD "<name>" inferred from current branch chief/<name>`) instead of falling back to `default`. Since `chief new` and the loop both put a PRD on its own `chief/<name>` branch, you land right back on the PRD you were working on just by checking out its branch and running `chief`. It only triggers when `.chief/prds/<name>/prd.md` actually exists, so a stray `chief/` branch is harmless; an explicit `chief <name>`/`--prd` still wins, and on `main`/`master` or a non-chief branch the old `default` → `main` → first-PRD → first-time-setup order is unchanged. The inference logic is now shared by the default command, `edit`, and `followup`
- **Frontend & testing grilling now applies to `chief edit` and `chief followup`, not just `chief new`** — the grill phases of `edit` and `followup` previously never mentioned the frontend or test seams, so a UI change or a follow-up with testable logic could slip through under-specified while `chief new` grilled both hard. Both prompts now grill the frontend when a change/item touches a UI (states, components to reuse, interaction, visual direction) and bake those decisions into the affected stories' acceptance criteria, and they sketch-and-confirm the test *seams* (existing/highest/fewest) when a change adds testable logic. This also makes the throwaway-HTML-prototype offer coherent in all three commands: the prototype block is now section-neutral and points the resolved decision at the stories' acceptance criteria (and a design section only where one exists), instead of naming a section that only `chief new` produces
- **`chief edit` infers the PRD name from the current branch** — like `chief followup` already did, running `chief edit` with no name from within a PRD's own `chief/<name>` branch now edits *that* PRD instead of silently falling back to `default`. The branch-inference logic is shared between the two commands
- **`chief followup` — turn a follow-up inbox into stories** — closes the loop for the work you find *after* a PRD is implemented. While reviewing the finished feature by hand you inevitably collect small fixes and polish items; drop them as a flat markdown checklist into a `todos.md` (or `followups.md`) inside the PRD's directory. `chief followup [name]` launches the agent, which reads that inbox plus the existing `prd.md` and converts each **open** (`- [ ]`) item into a proper `### US-XXX` story appended to `prd.md`: `Status: todo`, the **next available sequential ID** (no separate range), and — when the follow-up refines an already-`done` story — a `**Blocked by:**` line recording that story's ID purely as a lineage note (a done blocker never holds the story back). Existing `done` stories are never reopened, so the one-commit-per-story history stays intact, and the normal loop picks up the new stories on the next run. It reuses the same batch-grill/Opus-exploration machinery as `chief new`/`chief edit` but leans on the escape hatch: clear items are converted directly, only genuinely ambiguous ones get grilled. After writing, it flips the consumed inbox items to `- [x]` with their new story ID, so re-running is idempotent. Prompt-only conversion — it never writes implementation code. To make the inbox discoverable, `chief new` now scaffolds an empty (comment-only) `todos.md` next to `prd.md` when it creates a PRD; an existing inbox is never overwritten
- **Two-axis review + code-smell baseline** — the review agent's built-in prompt now reviews along two explicitly separated axes so a pass on one never masks a failure on the other: **Spec** (does the diff meet the story's acceptance criteria — partially-met criteria, missed edge cases, scope creep, missing/weak tests at the wrong seam) and **Standards** (is it good code for *this* repo). The Standards axis gained a concrete vocabulary — a baseline of Fowler code smells (mysterious names, duplicated code, feature envy, data clumps, primitive obsession, repeated switches, shotgun surgery, divergent change, speculative generality, message chains/middle man, dead code) — framed strictly as *judgment calls, not hard violations*: the codebase's established patterns and anything the tooling already enforces override the baseline, and a smell is never a reason to invent a refactor, keeping the reviewer from bloating a story's commit. This is prompt-only and applies to every provider; no config change needed. Adapted from Matt Pocock's engineering code-review skill (the parallel report-only sub-agents were deliberately not adopted, since Chief's reviewer fixes inline and folds into one commit)
- **`review.enabled` flag** — now that the built-in review prompt is strong on its own, you can turn the review on with just `review.enabled: true` and neither a skill nor instructions. `review.skill` and `review.instructions` still enable the review on their own (and remain optional, additive augmentations), so this flag is only needed to run the bare baseline
- **Story dependency edges + frontier-based selection** — stories can now declare cross-story ordering with an optional `**Blocked by:** US-001, US-002` line: a comma-separated list of story IDs that must be `done` before the story may start. Selection is no longer a flat priority sort. Chief still resumes any in-progress, non-parked story first, but otherwise it picks the lowest-`Priority` story on the *frontier* — the stories that are not done, not needs-review, and whose every blocker is already `done` — with ties broken by document order. This lets `Priority` do just one job (ordering among work that's actually unblocked) while real "this must come before that" constraints live in `Blocked by`. Parsing is deliberately forgiving so an authoring mistake can never deadlock the loop: an unknown/typo blocker ID is treated as satisfied, a self-reference is ignored, and duplicates are harmless. If nothing on the frontier is eligible but unfinished non-parked work still remains (a dependency cycle, or everything left is blocked by a parked `needs-review` story), Chief falls back to the lowest-priority unfinished non-parked story so the loop always makes progress. Fully backward compatible — a PRD with no `Blocked by` lines behaves exactly as it did before
- **Test-driven development at seams** — `chief new` now bakes testing strategy into the PRD and the loop instead of leaving it to chance. When a feature has testable logic, the generated PRD grows a **"Testing Decisions"** section that records the *seams* to test at (a seam is the public boundary where behavior can be observed without reaching inside — the guidance prefers existing seams, the highest seam, and the fewest, ideally one), what makes a good test here (verifying observable behavior through the public interface rather than implementation details), and prior art to mirror. During grilling the agent sketches the seams and confirms them with you; how the existing tests look is a fact it looks up, not a question it asks. The build agent then works **test-first in vertical slices** — one failing test, minimal code to pass it, repeat — testing at the named seam and steering clear of two anti-patterns: *implementation-coupled* tests (asserting private state, mocking internal collaborators, or querying a DB instead of the interface, so they break on a refactor even when behavior is unchanged) and *tautological* tests (the expected value is recomputed the same way the code does it, so it can never disagree — expected values must come from an independent source such as a known-good literal or the spec). The review agent now flags both anti-patterns too and checks that new behavior is covered at the right seam
- **Throwaway HTML prototypes during PRD grilling (Claude only)** — when a UI, layout, or interaction decision would be faster to settle by *seeing* it than describing it, the `chief new`, `chief edit`, and `chief followup` agents now proactively propose building a small, self-contained throwaway HTML prototype during their grill phase. It doesn't wait for a deadlock — it offers one whenever it would sharpen a decision, says what the prototype would show and which decision it resolves, and waits for your go-ahead (it never builds one unprompted). On approval it delegates the build to an **Opus subagent** (the same Opus-subagent pattern already used for codebase exploration), producing a single static `*.html` file with inline CSS/JS — no build step, no dependencies — written into the PRD directory under `.chief/`, which is never committed, so it can't pollute the repo. You open it, and your reaction resolves the decision; the decision itself is then captured in the PRD (Design & Frontend section plus the relevant acceptance criteria), which is the durable artifact. The HTML is disposable — throw it away or keep and reference it from the PRD — and never becomes the actual implementation. Claude only, since it relies on subagents
- **Separate review agent (replaces the inline review step)** — `review` no longer injects a "run this skill before you commit" line into the build agent's own prompt. Instead, once a story's build agent has committed, Chief spawns a **separate agent with a fresh context** that reviews the committed changes adversarially — it never sees the build agent's reasoning, so it acts like a colleague reviewing a PR rather than the author re-checking their own work. It fixes anything it finds and amends the story's commit (one commit per story stays intact). The config grew a free-form field so you can steer the reviewer beyond a skill: `review.skill` (optional project skill, Claude-only) and `review.instructions` (optional free-form guidance like "watch for N+1 queries and missing tests", works with any provider). Setting either enables the review. The review phase shows up in the log: when a review is configured the build agent's story marker reads `✓ Build done — review pending` in yellow (instead of the final green `✓ Story done`), then `🔍 Reviewing changes`, and finally a green `✓ Review complete` once the reviewer signs off — so it's clear the build agent's `<chief-done/>` isn't the last word. Best-effort: a review crash is logged but never un-completes the story
- **Per-story cost and token usage** — the story details panel now shows what each story cost and the tokens it burned (`Cost: ~$X · N out · N in · N cache`), live while a story is in progress and final once it's done. This required a new data source: the estimate previously relied on Claude's `result` event, which never arrives because the loop kills the process on `<chief-done/>`, so cost and token totals were almost always blank. Usage is now summed from every assistant message (input/output/cache-creation/cache-read) and cost is derived from a per-model price table (`internal/loop/pricing.go`, Opus/Sonnet/Haiku Anthropic list prices; unknown models show tokens without a cost). The running total in the header and the per-story cost column on the completion screen are now populated too. Note the cost is an estimate — cache-read tokens dominate on long Opus runs with a large reused context
- **Larger PRD names in the TUI** — PRD names are now given more room before they get truncated: the tab bar shows up to 16 characters (9 in the compact bar for narrow terminals, up from 8/5), and the PRD list (`l`) widens the name column from 12 to 20 characters. The picker modal grew from 60 to 72 columns so the wider names still leave room for progress and branch info
- **Archive & restore PRDs** — old PRDs no longer have to clutter the tab bar. In the PRD list (`l`), press `a` to archive the selected PRD: its directory moves from `.chief/prds/<name>/` to `.chief/archive/<name>/`, so it drops out of the tab bar but stays intact. Archived PRDs appear in an "── Archived ──" section at the bottom of the list, where `u` restores the selected one back into `.chief/prds/`. Archiving is blocked for a running PRD (stop it first) and, when the archived PRD is the one currently in view, the dashboard switches to the next remaining PRD. Fully reversible — nothing is deleted
- **Batch grilling in rounds** — the `chief new`/`chief edit` interview no longer trickles out one question at a time through a native picker. It now follows a *batch-grill* method: the agent maps the open decisions as a tree and, each round, asks the whole *frontier* of currently-answerable questions at once — numbered, each with a recommended answer — in plain prose, then waits for your batch of answers before recomputing the frontier for the next round. Faster to get through, and questions that depend on unanswered ones are held for a later round instead of being guessed at. The `AskUserQuestion` picker is no longer used
- **`chief new` creates the PRD branch up front** — when run inside a git repo, `chief new` now creates (or checks out) the `chief/<name>` branch immediately, the same branch the loop uses when the PRD is later run, so the PRD and its implementation stay off your default branch. A git failure only warns and lets PRD authoring continue
- **`chief new`/`chief edit` skip permission prompts** — the interactive Claude session now launches with `--dangerously-skip-permissions` (matching the autonomous loop), so the PRD interview reads the repo and writes `prd.md` without a permission prompt on every tool call (Claude only)
- **Codebase exploration always runs on Opus** — during `chief new`/`chief edit`, the agent now delegates repository exploration to an Opus subagent regardless of which model you picked in the model picker. This means a lighter session model (e.g. Fable) can drive the grilling/conversation to save cost without degrading how well Chief reads your codebase (Claude only)
- **`chief new` asks what you want to build first** — the PRD-creation prompt now runs an explicit "Phase 0" that asks, in plain prose, what you want to build and why *before* exploring the codebase or grilling. Previously the agent inferred the feature from the PRD name alone and dove straight into codebase analysis and multiple-choice questions. Codebase exploration and grilling now happen only after the goal is clear (and the open question is skipped when `context` is passed on the command line)
- **Model picker for PRD create/edit** — `chief new` and `chief edit` now open an interactive Claude model select before launching the session (Default, Opus, Sonnet, Haiku, Fable, or a custom model ID). The choice is passed to the Claude CLI via `--model`, which the interactive session previously ignored entirely. Shown only for the Claude provider and skipped when a model is pinned via `--model`
- **Light-terminal support & plain-text mode** — the TUI palette is now adaptive: lipgloss detects the terminal background and swaps the pale dark-mode greens/yellows for darker, higher-contrast tones on light terminals (no config needed). Setting `NO_COLOR` strips all styling to plain text, and `CHIEF_ASCII=1` replaces the emoji/Unicode icons (status markers, log tool cards, `🎉`/`💡`/`📋`/`🔄`) with ASCII fallbacks for terminals, multiplexers, or piped logs that render them poorly
- **Settings shortcut is discoverable** — `,` (open Settings) now appears in the dashboard/log footer and the `?` help overlay, instead of being hidden
- **Run summary on completion** — when a run finishes (or hits max iterations with committed work), Chief runs the agent once more to write a timestamped `summary-<date>-<time>.md` next to the PRD. The summary is **product-level** — what was built and what changed from the user's point of view, and **how to try it** (where to click, what looks different) — not a technical, file-by-file inventory. It is scoped to **exactly the commits this run made for the PRD's own user stories** (matched by their `feat: <ID> - <title>` subjects), so unrelated work sitting on the same branch — including same-numbered stories from other PRDs — never leaks in. Each run writes its own file (sortable, lowercase name), so a PRD keeps a history of its runs. The file is committed automatically (force-added so it lands even when `.chief/` is gitignored) and, when auto-push is on, rides along in the pushed branch/PR. On by default; toggle via settings (`,`) or `onComplete.summary: false` in `.chief/config.yaml`
- **Default PRD renamed `main` → `default`** — the unnamed PRD now lives at `.chief/prds/default/` to avoid confusion with git branch names ([#9](https://github.com/MiniCodeMonkey/chief/issues/9)). Existing `.chief/prds/main/` setups still load: bare `chief` falls back to `main` when no `default` exists. For `chief status`/`edit` on an old setup, pass the name explicitly (`chief status main`)
- **Desktop notification on completion** — when a run finishes, Chief pings the desktop (macOS `osascript`, Linux `notify-send`) so you don't have to babysit long loops. On by default; toggle via settings (`,`) or `onComplete.notify: false` in `.chief/config.yaml`
- **Per-story cost** — the dashboard shows a running USD total and the completion screen breaks cost down per story (Claude only; other providers don't report cost). Parsed from the agent's `result` event
- **Configurable watchdog timeout** — `loop.watchdogTimeoutSeconds` in `.chief/config.yaml` overrides the 5-minute default, so agents running long, silent builds or test suites no longer get killed as hung (`0` keeps the default)
- **Per-project code-quality review** — `review.skill` in `.chief/config.yaml` (e.g. `/code-quality`) makes the agent run a project-specific skill at the end of each iteration to review its changes against your standards, fix anything flagged, and only then commit. Because a story counts as done only once a matching commit lands, a review that blocks the commit automatically causes a retry. Empty by default (no review step)

### Bug Fixes
- **The stories panel no longer shows two percentages that contradict each other** — the panel title read `Stories (100%)` while the progress bar at the bottom of the same box read `40% 4/10`, which looks like a bug in the progress accounting and isn't one: the title's percentage was never about completion at all, it was the *scroll position* of the list (`storiesScrollOffset / maxOffset`), so `100%` meant "scrolled to the last story". Two bare percentages in one panel, one counting done stories in the current run and one counting scroll travel, cannot be told apart by looking at them. The title now names the visible slice instead — `Stories 11-20 of 20` — which carries the same information without a `%` to confuse with the bar underneath, and it reports the whole PRD's story count, so it also no longer looks like a second, disagreeing answer to "how many stories are there" next to the bar's run-scoped `4/10`. The range is computed *after* the scroll offset is clamped rather than before, so an out-of-range offset (a shrunken PRD, a resized terminal) can't briefly render a range past the end of the list. When every story fits on screen the title stays a bare `Stories`, exactly as before
- **The ETA now counts down between story completions** — the ETA was `avg × remaining stories`, a value that only changed the moment a story finished and otherwise sat frozen on screen even though the dashboard re-renders every second. Since the story currently in progress is one of the remaining stories, it already contributes a full `avg` to the estimate; Chief now subtracts the time already spent on that in-progress story (`time.Since(currentStoryStart)`) so the ETA ticks down each second. The subtraction is capped at one `avg`, so a story that overruns the average floors its own contribution at zero rather than eating into the other stories' budget, and the ETA never goes negative. With no story in progress the estimate is unchanged
- **The progress bar now tracks the current run, not the whole PRD** — the dashboard progress bar counted every story in `prd.md` (`completed / total` across the full list), so adding follow-up stories to an already-finished PRD made it regress: reopen a done 10-story PRD with `chief followup`, add 2 stories, and the bar started at `10/12` (83 %) instead of `0/2`. Follow-ups are ordinary appended `UserStory` entries with no run/batch marker, so there was nothing to distinguish this run's work from prior runs'. Chief now snapshots the IDs of the stories already passing when a run starts (in `doStartLoop`, after reloading `prd.md` so freshly-appended follow-ups are included) and counts only stories *outside* that baseline — so a follow-up run's bar starts at `0/2` and climbs to `1/2` (50 %), `2/2` (100 %) as this run's stories land. The baseline is keyed by story ID rather than a bare count, so a story that regresses (e.g. reopened by a re-review) can't skew the math. When you're only viewing a PRD without having started a run this session there's no baseline, so the whole PRD is counted exactly as before. The ETA already counted only unfinished stories (baseline stories are done, so they were never in it) and is unchanged; the completion screen still reports the whole PRD since it lists every story's timing
- **ETA now counts the review pass, and the story stays put while it's reviewed** — when a separate review agent is configured, a story isn't finished when the build agent commits: the reviewer still runs afterwards. But the per-story timing that drives the ETA was recorded at the build agent's `<chief-done/>` (`EventStoryDone`), so the whole review pass fell into an unmeasured gap and never counted — the ETA was systematically too optimistic. Timing is now finalized only once the review finishes (`EventReviewDone`), so a story's recorded duration spans build **and** review. With no review agent configured, timing still finalizes at build-done exactly as before. The TUI also no longer looks like it jumps ahead during a review: the story under review stays selected (pinned even across a `prd.md` reload) and is shown with a distinct **"Reviewing"** status — its own mauve `◍` icon — instead of a plain "In Progress" marker, so the review pass is visually separate from ordinary building and from the parked "Needs Review" state
- **`chief followup`'s checked-off inbox is now committed** — `chief followup` flips each ingested `- [ ]` item in the PRD's `todos.md` to `- [x]` with its new story ID, but chief's working-file commits only swept `prd.md`, `progress.md` and `.gitignore` — never the inbox. So after the follow-up stories ran and the PRD finished, the edited `todos.md` was left as a dangling uncommitted change every time. The per-story commit and the end-of-run summary commit now also stage the follow-up inbox (`todos.md` and its accepted aliases), so it lands with the run instead of lingering in `git status`
- **Follow-up run summaries no longer re-describe earlier runs** — the run summary is scoped by matching story commits by their `feat: <ID> - <title>` subject, but that match walked the *whole* branch history. On a `chief followup` run — which adds new stories to a PRD whose earlier stories were already committed on the same branch — the summary re-listed every previously-completed story as if this run had built it. Chief now captures the branch `HEAD` when a run starts and scopes the summary to `startRef..HEAD`, so a follow-up run's summary describes only the stories that run actually landed. Story-completion checks and the diff viewer still search the full history, so a story committed by an earlier run stays recognized as done
- **Quitting during a post-completion action now asks first** — on the completion screen the run summary (and any auto-push/PR) is generated in the background while the screen is shown, but `q`/`Ctrl+C` quit immediately: the loop was already finished, so the "a loop is still running" guard never fired, and the summary subprocess was killed mid-write, leaving no `summary-*.md` behind. Quitting while a post-completion action is in progress now opens the same confirmation dialog as a running loop (with wording that names the action), so an in-flight summary is no longer discarded by accident
- **ETA now appears reliably, including for background PRDs** — the completion estimate is driven by observed per-story durations, but those were tracked only for the PRD currently on screen and were wiped on every tab switch. When juggling several PRDs (or letting one run in the background while viewing another), the timing data was almost always empty, so no ETA ever showed. Timings are now kept per PRD, recorded for every running PRD regardless of which is on screen, and no longer cleared when switching tabs. The threshold to show an ETA also dropped from 3 completed stories to 2 (only the first, unrepresentative exploration story is skipped), so small PRDs get an estimate too
- **Progress markdown is readable on light terminals** — inline code in the progress panel (`` `Foo` ``, file paths, method names) used glamour's default bright red on a grey block, rendered with a fixed dark theme regardless of the terminal background. On light terminals this showed up as an unreadable dark-red box. The progress renderer now matches the terminal background (light/dark) and styles inline code as a calm cyan accent with no background box
- The agent and its whole subprocess tree are now killed together (the agent runs in its own process group). Previously only the direct child was killed, orphaning the tool and MCP subprocesses it spawned, which piled up across iterations
- A warning is surfaced when the working directory is not a git repo: `<chief-done/>` can't be commit-verified and work isn't persisted between fresh-context iterations
- Stories are only marked `done` when a matching commit actually landed. If the agent emits `<chief-done/>` without committing (forgot, a hook rejected it, or it crashed), the story is treated as a failed attempt instead of being falsely completed, so uncommitted work is no longer silently lost
- `prd.md` is now written atomically (temp file + rename), so a crash mid-write can never truncate the source of truth. The file watcher survives atomic replacement (also fixes spurious "removed" events from editors that save atomically)
- Auto-push and auto-PR on completion only run when the branch has at least one commit, so a run with no committed work no longer creates an empty branch or pull request
- **Parallel-PRD deadlock closed** — `Manager.Start` took the per-instance lock and then reached for the manager-wide lock, the reverse of the order `GetAllInstances`/`GetRunningPRDs` use. With several PRDs running while the dashboard polled their state, that AB-BA ordering could deadlock under load. Start now snapshots the manager fields it needs under the manager lock first, then takes the instance lock, so the two are always acquired in the same order
- **Run logs no longer interleave mid-line** — the agent's stdout and stderr are logged from separate goroutines that wrote to the log file without synchronization, so lines could splice into one another and corrupt the stream-json log. Writes are now serialized behind a dedicated mutex
- **Failed `prd.md` status writes stop the run instead of looping forever** — marking a story `done` or parking it `needs-review` is the source of truth for what's left to do, but a failed write was silently swallowed, so the loop would pick the same story again on the next iteration and never make progress (burning iterations). The failure is now logged, surfaced as an error event, and stops the run so the cause (e.g. a read-only filesystem) can be fixed

### Performance
- **Build agents delegate broad codebase research instead of crawling the repo inline (Claude only)** — exploring the repository is the most expensive thing a build agent does, and not because any single command is costly: every tool turn re-sends the entire conversation, so a few hundred small `grep`/`cat` turns cost quadratically and crowd out the context the actual work needs. A measured run averaged ~117 turns per agent, with three quarters of its whole bill going into re-reading context rather than producing code. The build prompt now tells the agent to hand broad questions — where a pattern lives, which files touch a concept, how a similar feature is wired, what the conventions are — to a subagent (the Explore agent when available, otherwise general-purpose) and work from its answer, and to read files with the **Read tool** rather than `cat`/`sed`/`head`/`tail`. Targeted searching it runs itself stays fine; that's what Grep and Glob are for. The block carries its own rationale so the agent doesn't dismiss the rule as arbitrary the first time delegating feels like a detour. Gated exactly like the existing explore-model and prototype blocks, so every non-Claude provider gets a byte-identical prompt to before
- **The build agent reads `progress.md` selectively instead of whole** — `progress.md` grows by a report per story, and the build prompt pointed the agent at the file with no guidance, so a run's own history was dragged through every turn of every later story — the file is at its largest exactly when the remaining stories are most expensive. The prompt now asks for the Codebase Patterns section plus the last one or two entries, and explicitly *not* the whole file. Prompt-text only: Chief still inlines nothing from `progress.md`, the append-only and patterns-upkeep instructions are unchanged, and a project without a `progress.md` behaves exactly as before — both nailed down by tests at the loop seam
- **Tab bar no longer rescans every PRD on each streaming chunk** — `tabBar.Refresh()` re-reads and re-parses every `prd.md` from disk, and it was called on every loop event. Streaming events (assistant text, tool calls, token usage) fire many times per second, so each chunk triggered a full directory scan of `.chief/prds/`. Refresh now runs only on events that change a tab's displayed state (iteration start, story done/needs-review, complete, error, max-iterations)
- **Lock-free liveness tracking in the loop's hot path** — the agent-output reader took the loop's mutex on *every* line just to stamp `lastOutputTime`, contending with the watchdog and every getter on high-volume JSON streams. It is now an `atomic.Int64` (Unix nanos), so the per-line path and the watchdog read/write it without locking
- **Regexes compiled once instead of per call** — the PRD-name validator (ran on every keystroke in the name field) and the story-status heading matcher (ran on every status write) compiled their regex on each invocation. Both now use package-level regexes
- **Static styles hoisted out of per-frame render paths** — ~200 `lipgloss.NewStyle()` calls sat inside `View()`/`Render()` methods that run every frame (the completion screen re-styles every 50 ms while the confetti animates). The static ones moved to package-level vars in `styles.go`, and glamour markdown rendering in the details panel is now memoized per `(markdown, width)` instead of re-rendered each frame
- **`progress.md` parsed in a single scan** — `ParseProgress` and `ParseTimings` each opened and scanned the same file with the same regexes; callers needing both read the file from disk twice. A new `ParseProgressFile` does one scan and the two functions are thin wrappers

### Refactoring
- **CLI parsing extracted into `internal/cli`** — `cmd/chief/main.go` (667 lines) mixed subcommand dispatch, flag parsing, PRD-path resolution, provider setup and ~70 lines of ASCII art in one untested file. Argument parsing (`ParseArgs`, `AgentFlags`, `PRDPathFromArg`) and PRD lookup (`FindAvailablePRD`/`ListAvailablePRDs`) now live in a unit-tested `internal/cli` package that returns errors instead of calling `os.Exit`; help text and the ASCII art moved to their own file. `main.go` drops to 373 lines and is a thin orchestrator
- **Central PRD path helpers** — the `.chief/prds/<name>/prd.md` convention was hardcoded in ~15 places. New `prd.PRDDir`/`prd.PRDPath` helpers (alongside the existing `PrdsDir`) centralize it so a layout change is a one-line edit
- **git command helpers** — the `internal/git` package repeated the same `exec.Command("git", …)` / `cmd.Dir` / output-and-error dance ~34 times. Three helpers (`runGit`, `runGitRaw`, `runGitChecked`) fold it together and centralize error handling, trimming `git.go` from 303 to 253 lines with no behavior change
- Added test coverage for the cost/pricing table (`internal/loop/pricing.go`) and `git.IsChiefIgnored`, plus full coverage of the new `internal/cli` package
- **`internal/tui/app.go` split from 2808 to 1428 lines** — the file was a single God-object acting as model, controller and renderer for every screen. Its distinct concerns moved to their own files in the same package (no API change): `messages.go`, `loop_control.go`, `auto_actions.go`, `timing.go`, `ticks.go`, `picker_actions.go`, plus shared UI helpers in `modal.go`, `format.go`, `ansi.go` and `scrollable.go`
- **Modal and header rendering deduplicated** — `centerModal` was copy-pasted 8 times across the screens; it is now a single helper in `modal.go`, joined by a `modalBoxStyle`/`dividerLine` pair and a `headerBar` helper that collapse ~10 hand-built modal boxes and the 6 near-identical header renderers. A new `Scrollable` interface unifies the log and diff viewers, removing the paired `if ViewLog … else if ViewDiff` branches from the update switch
- **`Loop.Run` and the parsers decomposed** — the 170-line `Run` shed its story-completion/commit-gate logic into `finalizeStory` and its log setup into `openRunLog` (`finalize.go`); the process-exit classification became a pure, unit-tested `classifyExit`. The five agent parsers shared their `<chief-done/>` detection and line-decoding boilerplate into `parse_common.go`, the review concern moved into a `reviewer` type (`reviewer.go`) threaded via an explicit `iterationMode` instead of a shared flag, and the manager grew `lookup`/`snapshot` helpers that fold 7+ repeated locking blocks
- **`runTUIWithOptions` untangled and de-recursed** — the CLI entry point mixed provider resolution, PRD discovery, first-time setup, migration, error rendering and post-exit relaunch, using recursion to restart the TUI. It is now split into `resolvePRDPath`/`runFirstTimeSetup`/`maybeMigrate`/`handlePostExit` with the restart driven by a `for` loop, removing the unbounded recursion
- **Shared helpers across the small packages** — generic NDJSON parsing (`internal/agent/ndjson.go`) replaces three copied `CleanOutput` loops; a generic `fileWatcher[T]` (`internal/prd/filewatcher.go`) backs both watchers; `git` errors now wrap the failing command with `%w`, `GetDiff`/`GetDiffStats` share a `diffRange` helper, and `firstNonEmpty`, `resolveBaseDir`, `prd.ChiefDir` and `(*PRD).CompletedCount` remove scattered duplication
